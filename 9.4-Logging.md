Imagine you are driving a car. If something begins to fail under the hood, a dashboard light turns on—a gentle tire pressure warning, an oil service notice, or a flashing red engine alert.

In programming, **logging** is that dashboard. It is how your application reports what it is doing, keeps track of events while running in the background, and warns you when things go wrong.

Many beginners start by debugging their code using `print()` statements:

```python
print("Fetching user data...")
print("User data fetched successfully!")
print("Failed to save to database!")
```

While `print()` is okay for quick 10-line scripts, it quickly falls apart in real-world applications:

- **No timestamps:** You don't know _when_ something happened.
- **No severity levels:** An innocent notification looks identical to a catastrophic server crash.
- **Lost when closed:** Once the terminal window is closed, printed messages disappear forever.
- **Hard to silence:** To remove debug prints in production, you have to manually hunt down and delete dozens of `print()` lines.

Python's built-in **`logging` module** solves all of this cleanly. Best of all, it comes pre-installed with standard Python, so no external libraries or `pip install` commands are needed!

## 1. Getting Started with the `logging` Module

To use the module, simply import it at the top of your script:

```python
import logging
```

The logging module gives you a flexible, standardized way to record diagnostic messages to the console, to text files, or even to remote servers.

---

## 2. Understanding the 5 Standard Log Levels

Events in your program have different degrees of urgency. Python categorizes them into **5 standard log levels**, arranged from least urgent to most urgent:

1. **`DEBUG`** (Level 10): Detailed technical info, typically only interesting when hunting down bugs.
2. **`INFO`** (Level 20): Confirmation that things are running according to plan (e.g., "Server started", "Connected to database").
3. **`WARNING`** (Level 30): An indication that something unexpected happened or may cause problems soon, but the software is still working (e.g., "Disk space low", "Deprecated function called"). **This is Python's default level.**
4. **`ERROR`** (Level 40): A serious issue that prevented a specific function or task from executing (e.g., "Could not open file", "API request timed out").
5. **`CRITICAL`** (Level 50): A catastrophic failure indicating that the entire application may be unable to continue running.

### Trying Out the Log Levels

Let's see what happens right out of the box (as seen in `testing.ipynb`):

```python
import logging

logging.debug("debug")
logging.info("info")
logging.warning("warning")  # Default log level
logging.error("error")
logging.critical("critical")
```

**Output in Terminal (stderr):**

```text
WARNING:root:warning
ERROR:root:error
CRITICAL:root:critical
```

### Why Did `debug` and `info` Not Print?

Notice that `logging.debug()` and `logging.info()` produced no output at all!

By default, Python sets the logging threshold to **`WARNING`**. Any message with a priority lower than `WARNING` (such as `DEBUG` and `INFO`) is ignored and silenced. Only messages at `WARNING`, `ERROR`, and `CRITICAL` will appear.

Notice also the output format:
`WARNING:root:warning` -> `[LEVEL]:[LOGGER NAME]:[MESSAGE]`
By default, messages run through Python's default root logger and print directly to your terminal.

## 3. Configuring Logging with `logging.basicConfig()`

To control the minimum severity level, route logs to a file, or change how log entries look, use `logging.basicConfig()`.

### Common Configuration Parameters

- **`level`**: Sets the minimum severity threshold (e.g., `level=logging.INFO` or `level=logging.DEBUG`).
- **`filename`**: Specifies a file where log messages should be written instead of showing up in the terminal.
- **`filemode`**: Decides file write behavior:
  - `'a'` (Append - default): Appends new log entries to the end of the existing file without erasing old ones.
  - `'w'` (Write / Overwrite): Clears the file fresh every time your program starts.
- **`format`**: Customizes the layout of the log line using formatting directives.

### Useful Format Directives

- `%(asctime)s`: Human-readable date and timestamp when the log occurred.
- `%(levelname)s`: Text logging level (`INFO`, `WARNING`, `ERROR`, etc.).
- `%(message)s`: The actual log text you passed.
- `%(name)s`: The name of the logger emitting the event.
- `%(filename)s`: The Python source file name where the log call was made.
- `%(lineno)d`: The line number in your source file where the log occurred.

### Code Example: Writing Formatted Logs to a File

Here is the setup from `temp.py`:

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    filename='custom_log.log',
    filemode='w',
    format="%(asctime)s - %(levelname)s - %(message)s"
)

logging.debug("This debug message will be ignored because level is INFO")
logging.info("Application initialized successfully")
logging.warning("User attempted login with outdated client version")
logging.error("Database connection dropped")
logging.critical("System out of memory!")
```

**Contents of `custom_log.log`:**

```text
2026-09-10 18:30:15,123 - INFO - Application initialized successfully
2026-09-10 18:30:15,124 - WARNING - User attempted login with outdated client version
2026-09-10 18:30:15,125 - ERROR - Database connection dropped
2026-09-10 18:30:15,125 - CRITICAL - System out of memory!
```

> **Beginner Note on Jupyter Notebooks:** `logging.basicConfig()` only configures the root logger once if it hasn't been initialized yet. If you run a cell with `logging.warning()` first (like in `testing.ipynb`), Python immediately attaches a default handler to your console. Calling `logging.basicConfig()` in a later cell won't override that existing handler unless you restart the notebook kernel or pass `force=True` (available in Python 3.8+).

## 4. Using Module-Level Loggers (`logging.getLogger(__name__)`)

Calling `logging.info(...)` uses Python's shared "root" logger. While convenient for tiny test scripts, using the root logger everywhere causes problems as your project grows.

If your project has 10 files and 3 third-party packages, all logging to "root", you will have no idea which module or file produced an error message!

### The Best Practice: `logger = logging.getLogger(__name__)`

Instead of calling `logging.info()` directly, create a dedicated logger for your specific file:

```python
logger = logging.getLogger(__name__)
```

### Why Use `__name__`?

In Python, the built-in variable `__name__` holds the name of the current file or module:

- If the file is being executed directly, `__name__` is `"__main__"`.
- If the file is imported (e.g., `import auth_service`), `__name__` is `"auth_service"`.

This immediately tags every log entry with the exact module that created it!

### Singleton Behavior: No Duplicate Loggers

The `logging.getLogger()` function acts as a **singleton registry**:

- If a logger with the given name already exists, Python returns the existing instance.
- It will **not** recreate or duplicate loggers.
- Multiple files or functions can safely call `logging.getLogger(__name__)` without wasting memory or conflicting.

### Code Example:

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    filename='custom_log.log',
    filemode='w',
    format="%(asctime)s - %(name)s - %(levelname)s - %(message)s"
)

# Create a module-level logger
logger = logging.getLogger(__name__)

logger.info("Basic info from module logger")
```

**Contents of `custom_log.log`:**

```text
2026-09-10 18:30:43,558 - __main__ - INFO - Basic info from module logger
```

## 5. Taking Full Control: Handlers and Formatters

In `temp.py`, we see a more advanced and powerful architecture:

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    filename='custom_log.log',
    filemode='w',
    format="%(asctime)s - %(levelname)s - %(message)s"
)

logger = logging.getLogger(__name__)

handler = logging.FileHandler("test.log")
formatter = logging.Formatter("%(asctime)s - %(name)s - %(levelname)s - %(message)s")
handler.setFormatter(formatter)
logger.addHandler(handler)

logger.info("basic info from module logger")
```

To understand how this works, think of the logging module as a team made of three distinct roles:

1. **The Logger (`logger`):** The spokesperson. Your application code talks directly to it (`logger.info(...)`).
2. **The Handler (`handler`):** The delivery person. It decides _where_ the message is sent (to a file, to the terminal screen, to an email alert, or across the network).
3. **The Formatter (`formatter`):** The stylist. It dictates _how_ the message is structured and presented.

### Breaking Down the Code Step-by-Step

1. **Create a separate destination:**

   ```python
   handler = logging.FileHandler("test.log")
   ```

   `FileHandler` opens a file named `test.log` and writes incoming records into it.

2. **Define a dedicated format:**

   ```python
   formatter = logging.Formatter("%(asctime)s - %(name)s - %(levelname)s - %(message)s")
   ```

   Notice that this format includes `%(name)s`, which prints the logger's identity.

3. **Attach the formatter to the handler:**

   ```python
   handler.setFormatter(formatter)
   ```

   The handler now knows how to format records before saving them to disk.

4. **Add the handler to your logger:**
   ```python
   logger.addHandler(handler)
   ```
   The logger now routes records through this custom handler.

### Why Did the Message Appear in Both Files?

When you run `temp.py`, you will discover that:

- `test.log` contains:
  ```text
  2026-09-10 18:30:43,558 - __main__ - INFO - basic info from module logger
  ```
- `custom_log.log` also contains:
  ```text
  2026-09-10 18:30:43,558 - INFO - basic info from module logger
  ```

This happens because of **Logger Hierarchy & Event Propagation**:

- Loggers form a tree structure. All loggers you create are children of the root logger.
- When `logger.info(...)` is called, it hands the record to its own handlers (`handler`, writing to `test.log`).
- By default, `logger.propagate` is `True`. The record travels up to the parent (the root logger), which forwards it to its own handler (`custom_log.log`).
- If you ever want a custom logger to log ONLY to its own handlers and not propagate upward, simply set `logger.propagate = False`.

## 6. Popular Real-World Use Cases of Logging

Now that you understand the basics from `temp.py` and `testing.ipynb`, here are four essential, real-world patterns used by professional Python developers.

### Use Case 1: Capturing Exceptions and Full Stack Traces

When code encounters a runtime error, beginners often catch it and print a simple message, losing the exact line number and error trace:

```python
# Bad practice:
try:
    result = 10 / 0
except Exception as e:
    print(f"Error: {e}")  # Where did it fail? What was the stack trace?
```

With logging, use `logger.exception()`. It automatically records the entire stack traceback into your log file!

```python
import logging

logger = logging.getLogger(__name__)
logging.basicConfig(level=logging.ERROR, filename='errors.log')

def divide_numbers(a, b):
    try:
        return a / b
    except ZeroDivisionError:
        logger.exception("An unhandled math error occurred during division")

divide_numbers(10, 0)
```

**Contents of `errors.log`:**

```text
ERROR:__main__:An unhandled math error occurred during division
Traceback (most recent call last):
  File "app.py", line 8, in divide_numbers
    return a / b
           ~~^~~
ZeroDivisionError: division by zero
```

Even if your program is running on a server unattended in the middle of the night, you will wake up to the exact line number, function, and cause of the failure.

### Use Case 2: Logging to Both Terminal (Console) and a File Simultaneously

During local development, you want to see logs instantly in your terminal, but you also want them saved to a permanent file for auditing.

You can attach both a `StreamHandler` (for the console) and a `FileHandler` (for the file) to the same logger:

```python
import logging
import sys

logger = logging.getLogger("multi_logger")
logger.setLevel(logging.DEBUG)

# 1. Console Handler (Shows warnings and errors on terminal)
console_handler = logging.StreamHandler(sys.stdout)
console_handler.setLevel(logging.WARNING)
console_format = logging.Formatter("%(levelname)s: %(message)s")
console_handler.setFormatter(console_format)

# 2. File Handler (Saves everything from DEBUG and above to file)
file_handler = logging.FileHandler("all_events.log", mode="a")
file_handler.setLevel(logging.DEBUG)
file_format = logging.Formatter("%(asctime)s [%(levelname)s] (%(name)s): %(message)s")
file_handler.setFormatter(file_format)

# Attach both handlers
logger.addHandler(console_handler)
logger.addHandler(file_handler)

# Emit messages
logger.debug("Connecting to cache server...")       # Only in file
logger.info("Cache connected.")                    # Only in file
logger.warning("Cache response took longer than 2s") # Both terminal and file
```

**Terminal Output:**

```text
WARNING: Cache response took longer than 2s
```

**Contents of `all_events.log`:**

```text
2026-09-10 18:35:01,100 [DEBUG] (multi_logger): Connecting to cache server...
2026-09-10 18:35:01,150 [INFO] (multi_logger): Cache connected.
2026-09-10 18:35:03,200 [WARNING] (multi_logger): Cache response took longer than 2s
```

### Use Case 3: Rotating Log Files (`RotatingFileHandler`)

If a busy production service writes to a single log file indefinitely, that file could grow to dozens of gigabytes and fill up your hard drive.

Python provides `logging.handlers.RotatingFileHandler` to automatically rollover files when they reach a certain size:

```python
import logging
from logging.handlers import RotatingFileHandler

logger = logging.getLogger("server_logger")
logger.setLevel(logging.INFO)

# Automatically roll over when file hits 5 MB (5 * 1024 * 1024 bytes)
# Keep at most 3 backup archive files: app.log.1, app.log.2, app.log.3
handler = RotatingFileHandler(
    "app.log",
    maxBytes=5 * 1024 * 1024,
    backupCount=3
)

formatter = logging.Formatter("%(asctime)s - %(levelname)s - %(message)s")
handler.setFormatter(formatter)
logger.addHandler(handler)

logger.info("Rotating file handler successfully configured")
```

Once `app.log` reaches 5 MB, it is automatically renamed to `app.log.1`, a fresh `app.log` is created, and old logs past backup 3 are discarded safely.

### Use Case 4: Logging in Web APIs (Flask / REST APIs)

In web applications like Flask, logging is essential for monitoring user requests, performance latency, and API error codes:

```python
from flask import Flask, request
import logging

app = Flask(__name__)

# Configure logging for our API
logging.basicConfig(
    filename='api_requests.log',
    level=logging.INFO,
    format='%(asctime)s - [%(levelname)s] - %(remote_addr)s - %(method)s %(url)s - %(message)s'
)

@app.before_request
def log_request_info():
    app.logger.info(
        "Request received",
        extra={
            'remote_addr': request.remote_addr,
            'method': request.method,
            'url': request.url
        }
    )

@app.route('/items/<int:item_id>')
def get_item(item_id):
    if item_id == 0:
        app.logger.warning(f"Invalid item ID requested: {item_id}")
        return {"error": "Item not found"}, 404
    return {"item_id": item_id, "name": "Sample Item"}, 200
```

**Example Log Output in `api_requests.log`:**

```text
2026-09-10 18:40:12,231 - [INFO] - 127.0.0.1 - GET http://localhost:5000/items/1 - Request received
2026-09-10 18:40:15,842 - [WARNING] - 127.0.0.1 - GET http://localhost:5000/items/0 - Invalid item ID requested: 0
```

## 7. Quick Reference Cheatsheet

Here is a quick summary of the essential tools and habits for logging in Python:

### Severity Hierarchy

- `DEBUG` (10) -> Detailed internal diagnostic data.
- `INFO` (20) -> Normal runtime confirmation messages.
- `WARNING` (30) -> Potential problem or unexpected event (Default level).
- `ERROR` (40) -> Feature failure or error preventing task execution.
- `CRITICAL` (50) -> Severe program-halting catastrophe.

### Quick Syntax Reminders

- **Import:** `import logging`
- **Fast configuration:** `logging.basicConfig(level=logging.INFO, filename='app.log', filemode='w')`
- **Module logger setup:** `logger = logging.getLogger(__name__)`
- **Log an exception:** `logger.exception("Descriptive message")` (inside an `except` block)
- **Custom file output:** `handler = logging.FileHandler("out.log")`
- **Custom line format:** `formatter = logging.Formatter("%(asctime)s - %(levelname)s - %(message)s")`
- **Combine handler and formatter:** `handler.setFormatter(formatter)` and `logger.addHandler(handler)`

### Do's and Don'ts for Beginners

- **Do** use `logger = logging.getLogger(__name__)` in every Python file so you always know where messages originate.
- **Do** use `logger.exception()` when catching exceptions to preserve stack traces.
- **Don't** use `print()` for critical errors or production runtime tracing.
- **Don't** log sensitive credentials, passwords, or personal user authentication tokens.
